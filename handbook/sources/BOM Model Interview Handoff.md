## Design method and guard against overly granular questioning

1. **Assemble the model while designing it.** Start with the entity roles and identities, the state/component responsibilities, the systems that change them, and the changes that must commit together. Explicit gaps are valid parts of a candidate map; exhaustive gameplay decisions are not prerequisites for drafting it. At this checkpoint, component responsibilities and coarse system ownership are accepted; the seven groupings in `ECS-007` are also accepted; remaining fields/encodings, unaccepted groupings, implementation partitioning, and execution order remain open.
2. **Use questions to resolve demonstrated model gaps.** Before asking a finer question, consider whether the alternatives change the shape or ownership of recoverable state, identity or reference lifecycles, system responsibilities, atomic changes, or a stable cross-team contract. If the answer only tunes an already representable gameplay policy, leave it as an explicit authoring or implementation choice unless the user wants to settle it. Keep unaccepted proposals outside the requirements.
3. **Group closely linked consequences in a clear proposal.** For example, a surviving body's behaviour switch and ID continuity can be presented together. A clear user answer ratifies only the scope actually presented; do not silently settle adjacent policies. Preserve one-question-at-a-time interaction where a question is needed.
4. **Trace representative situations through the map.** Use a grab, destruction/split, and death transition to expose missing state or responsibilities. Examples test the model; they do not authorize inventing details such as automatic attachment release, corpse destructibility, or round rules.
5. **Reassess the whole model after a few decisions.** If discussion keeps narrowing into one feature while the model remains unassembled, return to the overview and identify the next meaningful gap. Do not let the previous question, the largest open-question section, or a long implementation checklist determine the next topic automatically.
6. **Distinguish a missing fact from packaging and tuning.** The user explicitly redirected this discussion after component-boundary debates displaced concrete recoverable contents and lifecycles. If two groupings preserve the same canonical facts and ownership, show the choice as a candidate instead of treating it as a gameplay gap. For holds and connectors, identify the actual inputs and what survives a change. Do not invent extra fields merely to fill a named component. Quantitative cutoffs can remain configurable when their state/identity meaning is already settled.

The Open Questions document's P0/P1/P2 labels describe implementation need. They are not the interview order, and not every P0 must be resolved before a conceptual model can be useful. Choosing an ECS framework, geometry library, wire format, numerical threshold, or implementation slice is not the default next step for this design stage.

## Assembled map, data categories, and system responsibilities

The physical entity roles are environment pieces, living characters, and live bombs. They share body-motion, shape, and `MaterialProperties`, plus any further justified physical inputs, and add role-specific behaviour. Structural connectors and limb attachments have persistent relationship identities without their own bodies. Participant records and match progression are canonical match data; control assignment is a logical fact, not an additional physical relationship entity.

| Data category | Examples and boundary |
|---|---|
| Canonical | Identities, geometry, motion, gameplay configuration, persistent relationships, participant control references, bomb countdown state, and lasting match facts |
| Derived | Unity bodies/colliders/joints, meshes, solver caches, interpolation, reverse lookups |
| Authoring | Initial shapes/properties, composite layouts, connector settings; dependencies needed by reconstruction must be captured or resolved through a validated contract |
| Transient | Requests, interaction proposals, physics observations, explosion notifications, pending structural plans |

The following coarse system responsibilities are **accepted** under `ECS-006`. This is semantic ownership, not one class or pass per row or a chosen fixed-step sequence.

| Responsibility | Purpose |
|---|---|
| Input and interaction | Resolve control assignment and validate movement/attachment requests |
| Physics integration | Derive bodies and constraints; observe host motion, contacts, and loads |
| Gameplay evaluation | Evaluate character/death behaviour, bomb lifecycle, connector failure, and match progression |
| Structural resolution | Resolve geometry/identity/relationship outcomes and commit the complete change atomically |
| Reconstruction and replication | Rebuild derived machinery and give Odin committed semantic results and recovery state |

Representative transitions now have semantic outcomes: a validated grab creates one attachment with no duplicate character reference; a material split assigns all-new child IDs and resolves connectors/holds in the same commit; death changes body behaviour, clears participant control and outgoing holds, and preserves incoming holds on surviving locations. Landing activates canonical bomb-countdown state. These examples do not select exact records, physics callbacks, or further gameplay policies.

## How to record decisions at a checkpoint

1. **Collect the pending decisions and identify scope and status.** A clear answer to a precise proposal, including “yes,” can ratify the decision it actually answers; “lock it” is especially explicit. An unaccepted policy remains an open candidate outside the requirements. If the user has not answered a boundary, keep it open. Do not infer a decision from an older GDD, a branch, an example, or an assistant recommendation.
2. **Edit the Architecture as the current rule.** Add a stable rule ID or explicitly replace the old text. State the invariant or policy at the semantic level and mark ratified requirements **Accepted**, with explicit scope. Keep unresolved proposals in Open Questions. Keep Unity objects and canonical facts distinct. Do not leave two normative rules that disagree.
3. **Record why in the Decision Log.** Add the next `DEC-` entry with status, affected rule IDs, decision, rationale, and consequences or unresolved parts. If a rule is replaced, name the superseded decision and preserve its history rather than silently rewriting it away.
4. **Reconcile Open Questions.** Remove a question only when its whole issue is answered; otherwise narrow it. Add newly exposed gaps with related rules and a priority. An open question must never be silently answered by an example.
5. **Keep this handoff synchronized and check consistency.** Update the checkpoint date, baseline summary, open seams, and next activity where the batch materially changes them. Bump versions and dates for changed documents. Check affected rules and references for stale wording, and trace a relevant state transition for contradictions. Avoid rewriting unchanged material.
6. **Save the checkpoint in one batch.** Check for intervening versions, preserve each existing file's identity and version history, and save all affected originals before claiming the checkpoint is complete. Report the accepted decisions, remaining open items, changed files, and next activity. Share the current four-file set for the next agent. If any save fails, identify the incomplete checkpoint rather than claiming all files are synchronized.

A useful consistency check for every proposed rule is: Can a current snapshot reconstruct its lasting consequences? Is there one canonical source of the fact? Does a structural commit leave valid identities and references? Can Odin and Unity exchange semantic requests and committed results without serializing engine objects? Does level authoring or presentation depend on an assumption this rule has not actually made?
