# M5 protocol and clock extension (implementation contract)

Written before the M5 wire implementation. M4 remains a reproducible protocol-3 checkpoint. M5 changes the game protocol to 4 and the build ID to `BOM-scheduled-input-2026-11-06`. Transport BOM1, canonical structure version 2, quantization, reliable fragmentation and pose budgets stay unchanged. A v3 peer must fail the application handshake with a version/build reason before creating a player. This note records intended behavior, not a passing implementation claim.

## Time and schedule

Simulation steps remain 60 Hz. Server tick T identifies the state after step T; a command targeting T is consumed immediately before that step. A separate unfiltered server-time estimator never replaces the delayed presentation clock. Unreliable timestamp probes run every 250 ms, carry an exact u64 nonce and the local monotonic send time in the client's bounded outstanding table. The echo carries nonce, current server tick and f32 sub-tick phase at actual application-send time. The server's phase comes from its accumulator (clamped [0,1)); no client timestamp influences simulation. At receive time an estimate is `server_tick + phase + RTT*30`. Expired, duplicate, unknown-nonce, retransmitted or RTT>1s samples do not enter the estimator. These probes use no reliable retry.

Keep at most 64 accepted samples and 32 outstanding probes. Estimate RTT with an EWMA (alpha 1/8); compute positive one-way jitter p95 from the positive deviations of half-RTT from its EWMA. Select lead `clamp(ceil((RTT/2 + jitter95)*60)+2,2,15)`. Estimate server time by monotonic extrapolation from a bounded low-RTT sample window; adjust small offset errors by at most 0.05 tick per fixed command. During normal progress, a backward sample never reverses the accepted estimate. A fresh, ordered echo showing a discrepancy above eight ticks explicitly discards the old low-RTT window and reacquires server time, including a backward rebase if necessary; it marks synchronization incomplete before any further command is generated. A newly acknowledged input generation is required to resume. This covers a real server stall without spending minutes slowly correcting an obsolete estimate. A discrepancy >8 ticks, clock stall, or a required lead change that cannot be corrected without a repeated/skipped target enters resynchronization. Record raw clock error, RTT, jitter, desired/actual lead, pending slots and starvation. No clock is derived from Unity timeScale.

The server creates the initial input generation and schedule origin after authorization. Generation and sequence origins are u64. Connection identity is a server-assigned u64 incarnation (not a reusable player index). Initial synchronization advertises the incarnation, epoch and a proposed earliest target. Client requests/resets specify incarnation, epoch, new generation, first target and first command sequence. Server accepts only a strictly newer generation and a first target in `[current_tick+2,current_tick+32]`; reliable replies echo the exact accepted proposal and boundary. It rejects an obsolete/far-future proposal with current server time; the client retries with a new proposal, never remaps saved commands to another tick. Acceptance atomically flushes old slots and held/edge state. Old generation becomes terminal immediately; no new command executes until accepted. Until then movement is neutral.

## Commands and finalization

Unreliable input messages include incarnation, epoch, generation, render ACK and up to four exact commands, newest plus previous three. Each command contains u64 sequence, u64 target tick, finite quantized held movement and u64 jump-edge ID (zero means none). Redundancy is capped at four and fits one 1200-byte transport packet. The native fixed 60-Hz sender owns a 256-slot reconciliation ring. A schedule maps consecutive sequence numbers to consecutive target ticks; values remain integers even above 2^53. Wrapping u64 origins is rejected and resynchronized rather than ambiguously ordered.

The server keeps 32 future slots per authenticated incarnation. Validate matching epoch/generation, exact sequence-to-target mapping and target in `(finalized_through_tick,current_tick+32]`. Identical duplicates are harmless. A different payload for an occupied sequence/tick is a counted conflict and cannot replace the first accepted value. A finalized target is terminal too_late. Every simulation step finalizes its target, including absent/rejected slots. Missing held movement may carry for six consecutive missing ticks and then becomes neutral; jump and actions never carry. A jump ID cannot execute twice within a generation, including a repeated ID in a later target slot. Input resets clear the edge watermark. Track accepted, duplicate, conflict, too-late, wrong-incarnation/epoch/generation, starved and neutralized counts.

Owner state travels as a bounded unreliable message each tick, independently of the render-frame delta. It contains exact state tick, epoch, topology revision, incarnation, input generation, finalized-through tick, last actually applied sequence, missing-held count/fallback mode and teleport serial. Position/velocity/support velocity and coyote/buffer timers use unquantized f32. Grounded and stable support entity/cell keys are explicit. A zero support key means no identified support, never a Box2D address. Owner records cannot advance presentation topology. Owner ACK retires every local target <= finalization, including missing commands. Out-of-order owner state is ignored.

## Requests

Blasts and administrative commands use only the existing ordered reliable channel. Add incarnation, epoch and exact u64 request ID to the application envelope; do not also embed blasts in redundant held input. Maintain a per-incarnation 1024-result bounded terminal cache plus an eviction low-water mark. A duplicate returns its prior result, an evicted/old ID is rejected, and an unresolved entry is not silently evicted. Results include ID, status/reason, actual processing/effect tick and unique event ID. Existing host authorization, bounds, rate and solid-aim checks remain authoritative.

Blast intent carries estimated creation server tick and deadline <= creation+30 ticks. Reject future creation beyond the bounded clock allowance, expired intent, old epoch/incarnation and invalid aim. Local intent also expires after 500 ms. Processing occurs at the current server tick; timestamps do not rewind destruction. Administrative requests instead carry an explicit epoch precondition. Reset clears/terminates old-epoch pending requests. Reliable ordering alone is not the deduplication contract.

## Owner replay and collision validity

Prediction lives in the shared native client. Reuse the authoritative capsule construction, filter, tuning and player before/after movement helpers; factor the sandbox respawn policy out of the pure movement step. Audit every Player field and contact dependency before completing owner-state restore. Prediction restores authoritative position, velocity, timers, support and serial at the exact state tick, then replays only later target slots. Absent local slots use the same six-tick held fallback. The body is corrected immediately; only a separate visual offset decays over about 100 ms. Teleport/epoch/generation changes clear input and visual correction. Prediction-off retains authoritative interpolation and identical wire input.

First validate a static fixture. Retain 256 ticks of topology/pose history and use authoritative collision shapes, with a swept-neighborhood margin. Dynamic rigid and rubber proxies are kinematic, never whole-world physics prediction. Limit future extrapolation to six ticks (100 ms). Missing topology, incompatible revision, unknown entering geometry or uncertain support invalidates replay and enters explicitly logged conservative authoritative interpolation; recover within one second once sufficient valid history arrives. Players already pass through one another; any omitted bomb collision must be reported and measured. Never use the currently rendered fracture mesh as historical collision truth.

## Required evidence

Test the real UDP path, protocol-3 rejection, exact u64 values above 2^32/2^53, redundant/reordered/conflicting/late commands, reset rejection/retry and old generations, six-tick held fallback, one-shot deduplication/expiry/cache eviction, focus and epoch clears, complete owner restoration, 30/60/144-FPS identical target slots and payloads, prediction-off authority, moving/fracturing support fallback and recovery. Run the plan's two ten-minute static link profiles and retain correction/latency quantiles, snap reasons, clock/lead/starvation and backlog metrics. Passing the scheduler's unit fixtures alone does not pass M5.

Profile timing: let the connection/RTT estimator settle for twenty seconds on the static fixture, then reset measurement counters and collect the complete requested 600-second active window. Report the warmup duration separately. Held snapshots are refreshed from current physical input and coalesced natively when unchanged; distinct transitions retain their first timestamp, monotonic call order and the 256-entry capacity.

Implementation verified by M5 evidence. ABI 1.2 exposes full owner state, prediction stats, on/off, clear-intent, reset metrics and ordered terminal request results. Local result flag 4 identifies expiry/clear without a network effect; status 9 is local cleared. Queue age is subtracted from the exact whole creation tick without converting tick IDs through floating point. Profile cadence and actual Unity rendering are measured separately, and both pass the original response bound.
